## ★★ THE SCOPE QUESTION — hierarchy EXISTS (fully modeled + API-backed)
**Answer: DEAL(pool) → LOANS hierarchy is real and substantially built — NOT single-loan-only.** The deal picker + loan tape are **reconciliation of existing surfaces, not net-new**.

cre.db schema (the pool/loan spine):
- **`pool`** (2 rows) — shelf_name, vintage, seller, `current_tape_id`, `closed_at`.
- **`tape`** / **`working_tape`** — versioned loan tapes per pool.
- **`loan_in_pool`** (111 rows) — pool_id, **`deal_ref`** (→ links to an underwriting analysis), property_name, asset_type, `current_disposition_id`.
- **`loan_membership`** (667 rows) — tape_id, loan_in_pool_id, pool_id, status, tape_position.
- **`disposition`** (76 rows) — pool_id, loan_in_pool_id, originator_label, buyer_label, `override_flag`, supersedes, recorded_at, payload. **← the disposition log already exists.**
- **`analyses`** (8 rows) — the single-loan underwritings (Sunroad `ad9e9e90` is one). Linked from `loan_in_pool.deal_ref`.

So the chain is **pool → tape → loan_in_pool → analysis**, with dispositions + membership fully persisted. The frontend **already has** the routes: `/pools`, `/pools/[poolId]`, `/pools/[poolId]/loans/[loanInPoolId]`.
